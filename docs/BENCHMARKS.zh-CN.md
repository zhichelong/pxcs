# 基准测试

下面的数字全部来自同一台机器、同一批私有语料。数据集名称替换为 `A01`…`A15`，
规模、图片数和压缩率没有改动。

- CPU：i7-13700HX（16 核 / 24 线程）
- 内存：32 GiB
- 存储：`A01`–`A12`、`A14`、`A15` 在 NVMe 上；`A13` 在 USB 机械硬盘上
- Python 3.11.9，PXCS 1.4.0
- 测试台：`tools/pxcs_suite.py`，归档写到临时目录、每个数据集跑完即删；全部通过 `verify`

## 字节花在哪

`A14` + `A15` 的合计（源 43.3 GiB，归档 16.7 GiB）：

| reason | 条目 | 源大小 | 占用 | 占归档 |
|---|---:|---:|---:|---:|
| `residual_lossy` | 6 671 | 34 380 MiB | 12 239 MiB | 60.3% |
| `key_lossy_passthrough` | 1 796 | 8 608 MiB | 6 840 MiB | 33.6% |
| `residual_larger_than_source` | 226 | 1 096 MiB | 1 096 MiB | 4.3% |
| `zlib`（非图片文件） | 71 | 343 MiB | 342 MiB | 1.5% |

`key_lossy_passthrough` 的意思是「这个分辨率在集合里只出现一次」，没有邻居可以做差分；
这部分由 `jpegxl` 编码器压到源大小的 79.5%。`residual_larger_than_source` 是差分化之后
反而更大的兜底。

完全没有差分的集合（`A01`、`A04`、`A06`）的改进全部来自 JPEG XL：
98.9% → 83.5%、95.3% → 79.2%、98.4% → 81.5%。

## 吞吐与资源

| 指标 | 数值 |
|---|---|
| `create` 吞吐 | 全语料平均 16.8 MB/s |
| CPU 占用 | 24 逻辑线程的 27–45% |
| 峰值工作集 | 5.0–8.1 GiB（预算 = 物理内存的 60%） |
| `verify`（397 条归档） | 147.3 s → 59.8 s，8 线程（2.46×） |
| `extract`（同一归档） | 621.2 s → 107.8 s，8 线程（5.76×） |
| JPEG XL 编码 | 约 9 MB/s 每线程 |
| JPEG XL 解码 | 约 11 MB/s 每线程 |

峰值内存跟着预算走，而不是跟着数据集大小走：内存护栏会把并发压下来，而不是让进程被
系统杀掉。

## 已知天花板

`create` 没有吃满机器。JPEG 集合的 CPU 时间里约 83% 在 libjxl（C 库）里，17% 是 Python
胶水；墙钟效率还受「按顺序提交」的落盘路径限制——必须等最早的那个在跑组提交完才能继续
提交新的。测量细节见 [VALIDATION.zh-CN.md](VALIDATION.zh-CN.md)。补这个缺口是待办工作，
不是归档格式本身的语言限制。

## 复现

语料是私有的。要在自己的集合上跑同一套测试台：

```powershell
copy datasets.example.json datasets.json   # 然后改路径
python -m tools.pxcs_suite --list
python -m tools.pxcs_suite --all --out report.json
```

`datasets.json` 已在 `.gitignore` 里。

## 1.4.1：参考树 vs 星形

1.4.1 把"组内星形"（所有变体都对着一张关键帧差分）换成参考树：每个成员参考
"比它先规划、且最相似"的成员，有损残差深度上限 6、无损 8。

9 个图集，2026-11-20，同机同线程数（12）。`1.4.0` 是 GitHub 上已发布的版本。

| ID | 内容 | 规模 | 1.4.0 | 1.4.1 | 变化 |
|---|---|---:|---:|---:|---:|
| A16 | PNG，完整差分集 | 53.9 GiB | — | **16.3%** | — |
| A17 | PNG，单角色 177 张变体 | 1.3 GiB | 26.8% | **10.2%** | −16.6 pt |
| A18 | JPEG，中型差分 | 10.6 GiB | 66.7% | **59.3%** | −7.3 pt |
| A19 | PNG，混合 | 2.1 GiB | 42.0% | **37.2%** | −4.8 pt |
| A20 | JPEG，中型差分 | 2.7 GiB | 16.1% | **11.8%** | −4.3 pt |
| A21 | JPEG，庞大差分 | 13.8 GiB | 31.1% | **28.6%** | −2.4 pt |
| A22 | PNG，混合 | 3.7 GiB | 39.5% | **38.1%** | −1.4 pt |
| A23 | PNG，散图 | 1.7 GiB | 77.0% | 76.2% | −0.7 pt |
| A24 | JPEG，散图 | 3.1 GiB | 80.8% | 80.6% | −0.2 pt |
| A25 | JPEG，散图 | 1.5 GiB | 79.3% | 79.3% | 0.0 pt |

**散图没有收益**——没有邻居可以差分，多算一遍缩略图还会略慢。变体集收益 1.4–16.6 个
百分点，且随"共享同一底图的变体数量"增长。

速度不是单调的：残差变小后压缩更快，多数变体集反而更快（A18、A22 提升最明显）；
少数因为逐层编码变慢。

代价在解码深度：冷缓存解一张 depth-6 条目约是关键帧的 2.2 倍；顺序提取会复用父缓存。


## 1.5.0：读取加固与内存/速度调整

格式没有变化，压缩率也没有变化；这一版验证的是"加固没有拖慢正常路径"。

| 指标 | 1.4.1 | 1.5.0 |
|---|---:|---:|
| 归档体积（60 张 JPEG / 758 MiB） | 50.48 MiB | 50.48 MiB（+1 B，来自随机 archive_id） |
| 创建耗时（交错 A/B，两次） | 37.9 / 37.1 s | 37.1 / 37.0 s |
| `verify` full | 64.4 s | 58.0 s |
| `verify` quick | 62.4 s | 0.35 s |
| 创建峰值 RSS | 5.9 GiB | 5.35 GiB |
| 参考树规划峰值（n=1000 / n=3000） | 约 2 GB / 32 GB 临时量 | 5.9 MB / 17.7 MB |

`verify --quick` 的差距不能直接当成"快 180 倍"：1.4.1 的 quick 对残差条目仍然整链
重建（和帮助文案矛盾），1.5.0 的 quick 只校验 payload CRC/SHA。这是语义修正，
不是纯性能优化。同一份归档上 `test_full` 仍然走完整解码，快了约 10%。

与显式 `folder`：
