# 基准测试

下面的数字全部来自同一台机器、同一批私有语料。数据集名称替换为 `A01`…`A15`，
规模、图片数和压缩率没有改动。

- CPU：i7-13700HX（16 核 / 24 线程）
- 内存：32 GiB
- 存储：`A01`–`A12`、`A14`、`A15` 在 NVMe 上；`A13` 在 USB 机械硬盘上
- Python 3.11.9，PXCS 1.4.0
- 测试台：`tools/pxcs_suite.py`，归档写到临时目录、每个数据集跑完即删；全部通过 `verify`

## 字节花在哪

`A14` + `A15` 的合计（源 43.3 GiB，归档 16.7 GiB）：

| reason | 条目 | 源大小 | 占用 | 占归档 |
|---|---:|---:|---:|---:|
| `residual_lossy` | 6 671 | 34 380 MiB | 12 239 MiB | 60.3% |
| `key_lossy_passthrough` | 1 796 | 8 608 MiB | 6 840 MiB | 33.6% |
| `residual_larger_than_source` | 226 | 1 096 MiB | 1 096 MiB | 4.3% |
| `zlib`（非图片文件） | 71 | 343 MiB | 342 MiB | 1.5% |

`key_lossy_passthrough` 的意思是「这个分辨率在集合里只出现一次」，没有邻居可以做差分；
这部分由 `jpegxl` 编码器压到源大小的 79.5%。`residual_larger_than_source` 是差分化之后
反而更大的兜底。

完全没有差分的集合（`A01`、`A04`、`A06`）的改进全部来自 JPEG XL：
98.9% → 83.5%、95.3% → 79.2%、98.4% → 81.5%。

## 吞吐与资源

| 指标 | 数值 |
|---|---|
| `create` 吞吐 | 全语料平均 16.8 MB/s |
| CPU 占用 | 24 逻辑线程的 27–45% |
| 峰值工作集 | 5.0–8.1 GiB（预算 = 物理内存的 60%） |
| `verify`（397 条归档） | 147.3 s → 59.8 s，8 线程（2.46×） |
| `extract`（同一归档） | 621.2 s → 107.8 s，8 线程（5.76×） |
| JPEG XL 编码 | 约 9 MB/s 每线程 |
| JPEG XL 解码 | 约 11 MB/s 每线程 |

峰值内存跟着预算走，而不是跟着数据集大小走：内存护栏会把并发压下来，而不是让进程被
系统杀掉。

## 已知天花板

`create` 没有吃满机器。JPEG 集合的 CPU 时间里约 83% 在 libjxl（C 库）里，17% 是 Python
胶水；墙钟效率还受「按顺序提交」的落盘路径限制——必须等最早的那个在跑组提交完才能继续
提交新的。测量细节见 [VALIDATION.zh-CN.md](VALIDATION.zh-CN.md)。补这个缺口是待办工作，
不是归档格式本身的语言限制。

## 复现

语料是私有的。要在自己的集合上跑同一套测试台：

```powershell
copy datasets.example.json datasets.json   # 然后改路径
python -m tools.pxcs_suite --list
python -m tools.pxcs_suite --all --out report.json
```

`datasets.json` 已在 `.gitignore` 里。
