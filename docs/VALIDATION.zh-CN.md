## 2023 差分图：旧版“几乎不压缩”的原因与新结果

数据：`<local-path>`，
1205 张 JPEG，7,813,160,846 B（7.277 GiB），61 个精确分辨率组。

旧 1.1 归档：7,594,745,234 B（97.20%），
1,156 raw（其中 1,101 `lossy_passthrough`）、49 `pxc_residual`。
根因不是分组：旧代码的 `_variant_key` 只匹配 `_pN`，而本组文件名是
`01_3191.jpg` / `01_31911_1.jpg` / `60_231.0.jpg`；当缩略图分数 ≥0.85
时它把候选列表清空，导致整组 raw。没有进入残差编码的组自然没有压缩。

新 1.2 在 `01_319*` 组（25 张，145.88 MiB）上的实测：

| 配置 | 归档 | 比例 | 时间 |
|---|---:|---:|---:|
| q12 + zlib 残差 | 62.88 MiB | 54.36% | 8.4s |
| q16 + zlib 残差 | 44.91 MiB | 43.10% | 7.8s |
| q8 + zlib 残差 | 107.69 MiB | 73.82% | 10.7s |
| q16 + PXC 残差（极慢） | 44.91 MiB | 30.79% | 160.8s |

q8 的 zlib 残差受 JPEG 噪声影响明显；q12 是当前默认的折中。
PXC 残差更小，但同组慢约 15–20 倍，暂不作为默认。

粗差安全说明：量化残差重建的是近似像素；`verify` 校验的是近似像素哈希。
需要像素级无损时用 `--delta-quant 0`，但 JPEG 噪声会让残差可能大于源文件，
此时自动回退 raw，压缩率接近 100%。

- 源：1,205 张 JPEG，7,813,160,846 B（7.28 GiB）；
- 归档：5,024,069,109 B（4.68 GiB），**64.30%**；

- `max_depth: 1`；

## 分卷行为确认

- 未启用分卷：输出单文件，minor=2，不产生 `.001`，旧程序仍可读；
- 卷名 `base.001` 起连续编号，卷头记录 `volume_index/logical_offset/length`；
- 读取时给任意一卷或基名都能定位整组；
- 缺卷：`缺少分卷: 002（完整范围 001..005）`；
- 错序：`分卷顺序错误: ...（期望 X，实际 Y）`；
- 截断：`分卷大小与卷头不符`；
- 数据损坏：`verify` 报 CRC/认证失败；
- 单张图片跨卷提取正常，随机提取能力未受影响。

## 加密行为确认

- 口令输入：`--ask-password`（getpass，不回显、二次确认）、
  `--password-file`（取第一行）、`--password-stdin`（取一行）；
  均不把口令写进 argv；
- 算法：Argon2id（默认 m=256 MiB / t=3 / p=4，约 0.26s）+ AES-256-GCM，
  子密钥用 HKDF-SHA256 分离；scrypt 作为备用；
- 口令校验：解密 AEAD 校验块，失败统一报“认证失败：口令错误或归档已被篡改/损坏”；
- 文件名加密：索引整体 AEAD，`zlib.decompress` 直接失败，字节中不含文件名；
- 文件名不加密：索引为 zlib(JSON)，但受 `index_mac`（HMAC-SHA256）保护；
- 篡改 payload / 索引 / 加密头都能被检测；
- 口令不会出现在 stdout/stderr/`repr(CreateOptions)` 中（有专门测试）。

## 多语言行为确认

- `language/chinese_simp.json` 集中管理 CLI 帮助、提示、错误、状态、进度文本；
- 键名为 ASCII 点分形式（如 `crypto.auth_failed`），不使用中文句子当键；
- 配置 `"language": "chinese_simp"` 或 `--language <code>` 切换；
- 缺翻译 → 当前语言 → `chinese_simp` → 键名；缺格式化参数 → 保留占位符；

## 1.3 已知限制

- 分卷没有冗余/纠错，丢失任何一卷都无法完整恢复；
- 加密不隐藏归档总大小、条目数和单条 payload 长度；
- `pxc_core`（PXC 单图 codec）内部的少量错误文本尚未迁移到语言文件，
  这些文本会在极端损坏场景下以中文出现（PXCS 产品层文本已全部迁移）；
- 单个 payload 需整体读入内存，超大图仍受内存限制，与分卷/加密无关。
- 默认不再完整解码 raw 直通的图片（见下一节），因此"头部正常但像素数据被
  截断"的文件不会被创建阶段发现，只会被原样归档；需要该校验时用 `--decode-raw`。

# Python 阶段 0：性能与可验证性（不涉及 C++）

这一轮不是加功能，而是把"值不值得重写"和"重写后怎么验收"两个问题先钉死。

## 1. 性能剖析：瓶颈不在算法

对 55 张真实图片（369 MB）做 cProfile，按自身耗时排序：

| 热点 | 自身耗时 | 占比 |
|---|---:|---:|
| Pillow JPEG 解码 `ImagingDecoder.decode` | 16.87 s | 56% |
| WebP 编码 `ImagingEncoder.encode` | 3.15 s | 10% |
| hashlib `update` | 2.74 s | 9% |
| `numpy.array` 转换 | 1.39 s | 5% |
| `bytes.join` / `ndarray.tobytes` | 2.21 s | 7% |
| `zlib.crc32` | 0.58 s | 2% |
| **PXC tile 编码** | **未进前 22** | **<2%** |

结论：自研的 tile 编解码几乎不耗时，时间全花在"解码 → numpy → bytes → 哈希"
这条数据搬运链上。这条结论直接决定了后续优化的对象。

## 2. 优化：raw 直通不再重复解码

JPEG/WebP 关键帧按原始字节直通保存（`codec=raw`）。此前创建时会把这些图完整
解码一次，只为算像素哈希——但实测**旧归档 107 个 raw 条目，0 个带
`pixel_sha256`**（`_raw_result` 从来不会写这个字段），所以这次解码没有产出任何
被保存的信息。现在：组内只有一张图（不可能差分）时完全不解码。

同一目录（55 张 JPEG / 369,517,918 B，默认参数）：

| 阶段 | 优化前 | 优化后 | 提升 |
|---|---:|---:|---:|
| create | 19.129 s（18.42 MB/s） | 1.183 s（297.98 MB/s） | 16.2× |
| verify | 23.921 s（14.73 MB/s） | 1.206 s（292.20 MB/s） | 19.8× |
| extract | 1.906 s | 1.392 s | 1.4× |
| list | 0.0028 s | 0.0028 s | — |

校验也一起变快，是因为 `verify_archive` 原先会对没有像素哈希的条目也无条件
`resolver.get()` 解码（解完却无哈希可比）。现在无哈希且非 `--quick` 时只做
payload 完整性校验。

### 差分组行为未变（真实数据验证）

同一分辨率目录（8 张 JPEG / 60,611,801 B，其中 7 张同尺寸）：

```
[OK] ... 57.80 MiB -> 27.96 MiB (48.37%) | 2 组 / 2 key | 8 图
     (6 差分, 6 有损差分, 2 原始) | 2.99s
[VERIFY] 检查 8/8 | 失败 0 | 有损差分 6
```

- 组内 7 张仍然解码、仍然差分（6 个有损差分），像素哈希照旧写入；

## 7. 修复：普通模式（拖文件夹）崩溃

用户实际跑出来的崩溃：

```
[SCAN] 正在读取 1290 个图片头，统计分辨率...
Traceback (most recent call last):
  File "pxcs_core\grouped_create.py", line 669, in create_grouped_archive
TypeError: t() got multiple values for argument 'key'
```

### 根因

i18n 引擎的签名是 `t(key, **kwargs)`，形参就叫 `key`；而分组输出这行文案
`create.group_line` 的模板里带 `{key}` 占位符，调用点传了 `key=group[0].source.rel`。
两者撞名，于是 `key` 既被当成位置参数又被当成关键字参数。

```python
print(t("create.group_line", index=..., width=..., ..., key=group[0].source.rel))
```

### 为什么测试没抓到

这条路径只有 `show_groups=True` 且非 quiet 时才会执行。**普通模式（拖文件夹）
默认 `show_groups=True`**，而其它所有测试都用 `CreateOptions()` 的默认值
`show_groups=False`。也就是说：**拖放入口一直是坏的，命令行 `create` 一直好的**，
测试恰好只覆盖了后者。

这是 1.3 多语言迁移引入的既有缺陷，与"阶段 0"的性能改动无关。

### 修复

把 `key` 改成**位置限定参数**（`/`），格式化参数里就可以自由使用名为 `key`
的占位符：

```python
def t(self, key: str, /, **kwargs: Any) -> str:   # pxc_core/i18n.py
def t(key: str, /, **kwargs: Any) -> str:         # 模块级快捷方式
```

这比"改文案里的占位符名"更彻底：以后任何语言文件都可以用 `{key}`。

### 回归防护

- `tests/test_pxcs_create_output.py`（5 个测试）：`show_groups=True` 必须打印
  分组行且带 `key=` 文件名；`--details` 路径；**普通模式 `pxcs <目录>` 的完整
  CLI 路径**（历史崩溃入口）。
- `tests/test_pxcs_i18n.py::test_all_placeholders_are_supplied`：静态扫描全部
  `t("键", ...)` 调用点，检查该文案需要的占位符是否都被提供。
- 全量静态审计结果：**341 个调用点，缺失占位符 0 处，未知键 0 处**。

## 8. Batch A：健壮性、诚实性、可用性

上一轮评估发现的三个 P0 问题，本轮修完。

### 8.1 单个文件读不了不再毁掉整次归档

**旧行为**：`_encode_key` 里 `Path.read_bytes()` 没有兜底，`write_group_key`
又是在主循环里同步调用的，异常一路冒到 `except BaseException: writer.abort()`。
1290 张、6 分钟的任务，只要一张图被占用（索引器、同步盘占位符、权限），
整次创建作废。对照：差分路径一直有 `collect_future` 兜底，只有 key 和非图片
文件没有。

**现在的契约**：

| 情况 | 行为 |
|---|---|
| 组 key 读不了 | 组内向后最多 8 个成员里挑一个顶替当 key，该组差分照常 |
| 普通成员读不了 | 记为跳过，其余成员照常 |
| 非图片文件读不了 | 只跳过它自己 |
| 整组前 8 个都读不了 | 全部记为跳过，归档仍然生成 |

实现要点：`_encode_key` / `_encode_delta` 拆成 `*_impl` + 一层安全包装，把
`PxcError/OSError/MemoryError` 统一转成 `_Result.error`；`_read_raw_result` 读
不到时返回 error 而不是抛异常；`finish_state` 对 `_write_result` 做双重兜底。

### 8.2 失败必须可见

- `CreateStats` 新增 `skipped`；
- 摘要末尾输出 `警告：有 N 个文件被跳过`，列出前 20 项，其余折叠；
- `--verbose` 逐个打印 `[SKIP] <路径>: <原因>`；
- **退出码 3** = 归档已生成但有跳过。

### 8.3 写完自检

`finish()` 之后立刻用 `ArchiveReader` 重开：核对索引长度与条目数。
失败抛 `PxcsSelfCheckError`，**归档文件保留**（便于事后 verify），**退出码 4**。
`--no-self-check` 可关。成本约一次 `list`（几毫秒）。

| 退出码 | 含义 |
|---:|---|
| 0 | 成功 |
| 1 | 条目级失败 / 其他运行错误 |
| 2 | 参数、口令错误或归档不存在 |
| 3 | create 完成但有文件被跳过 |
| 4 | create 写完后自检失败 |

## 9. 并发语义与内存护栏

用户反馈：`threads: 8, parallel_groups: 100` 跑不满 CPU，希望 `0/0` 表示跑满，
并且别因为跑满内存把图片加载搞挂。

### 9.1 根因

旧代码写死了两处：

```python
threads = opts.threads if opts.threads > 0 else min(8, cpu_count)   # 0 只给 8 个
parallel_groups = max(1, min(opts.parallel_groups, threads))        # 0 被钳成 1
```

24 核机器上 `threads=0` 只开 8 个 worker；`parallel_groups=0` 直接变 1。
两个"0"都不是"自动"，而是"最小值"。

### 9.2 新语义

| 配置 | 含义 |
|---|---|
| `threads = 0`（默认） | 用满所有核心 |
| `parallel_groups = 0`（默认） | 与 worker 数一致 |
| `memory_limit_mb = 0`（默认） | 按可用物理内存的 60% 自动 |

`DEFAULT_SETTINGS`、`config/config.json`、`CreateOptions` 三处默认值已统一为 0/0/0，
`settings.py` 的钳位下界也改成 0（原来 `min(1, …)` 会把 0 改回 1）。

### 9.3 内存护栏

新增 `pxcs_core/limits.py`：

- 工作集估算：`像素数 × 系数`（差分 5 倍 / 关键帧 3 倍 / raw 2 倍），最小 1 MiB；
- `MemoryBudget`：按字节记账的并发闸门，worker 解码前 `acquire`、`finally` `release`；
  预算不足时**排队等待**而不是 OOM；单任务超过预算时放宽到整个预算，避免饿死；
- 活跃组参考图：按 90 分位估算，最多占预算 50%（其余留给 worker）；
  因此总内存上界 ≈ 1.5×预算 = 0.9×可用内存；
- 预算被压低时启动日志会打印原因与数值，`--verbose` 打印峰值与排队次数；
- 新增 `--memory-limit SIZE`（`4G` / `2048M`）。

### 9.4 踩坑：用最大值估参考图会把并行度压死

第一版用"最大图"估参考图，结果 120 张那组把 `parallel_groups` 从 24 压到 **3**，
而实测内存峰值只有 **5.12 GiB / 7.70 GiB**，排队次数 0——护栏过度保守，
反而成了新的性能瓶颈。改成 90 分位 + 50% 比例后，同一场景恢复 24 组并行。

### 9.5 实测

**合成的 240 张 / 1.45 GiB（同分辨率差分组）**：

| 配置 | wall | CPU 占用 | 吞吐 |
|---|---:|---:|---:|
| `--threads 8` | 57.08 s | 26.6% | 25.5 MB/s |
| 默认（24 worker） | 38.39 s | 41.6% | 37.9 MB/s |
| `--threads 48`（超订） | 38.16 s | 42.9% | 38.1 MB/s |

8 → 24 线程是 **1.49×**；24 → 48 线程**没有任何收益**，说明瓶颈是 GIL，
不是 worker 数。

**用户真实目录 `<collection>`（1290 张 / 10.60 GiB / 179 组）**：

| 版本 | wall | 比率 | 说明 |
|---|---:|---:|---|
| 修之前（8 worker / 并行组 10） | 506.88 s | 79.18% | 首次实测 |
| 现在（24 worker / 并行组 24） | **391.16 s** | **79.18%** | 快 1.30×，产物一致 |

归档 `8.39 GiB`，770 差分 / 518 raw / 2 重复；`verify` 见下。

### 9.6 顺带修掉的坑：输入目录里的旧归档会被再打包

实测时把输出写在输入目录里，第二次运行发现"25 个文件 / 140.93 MiB"——
多出来的是上一次生成的 `a.pxcs`。原来的产物过滤只认"当前输出名 + 临时后缀"，
不认**其它名字的归档**，于是每跑一次体积就翻一倍。

已修：扫描阶段把 `*.pxcs` / `*.pxcs.001` 一律排除，并打印
`已跳过 N 个 .pxcs 文件/分卷`。有测试锁定（`test_existing_archive_in_input_is_skipped`）。

### 9.7 结论：Python 线程的天花板

24 核机器上默认配置只能到约 **42% CPU**。想达到 7z 那种吃满多核，必须走
**多进程**（每个进程独立 GIL）。那是一次架构改动：需要把"按组编码 + 集中写盘"
拆成 IPC 协议与偏移分配，代价与风险都不小，本轮**未实施**，作为下一步选项。

## 10. 本轮结论

- "重构前差什么"里，**规格**和**黄金向量**这两项硬阻塞已补齐；
- 第三个硬阻塞（验收标准）已落成 `pxcs_compare.py` + `CODEC.md` §8，
  明确"不能比整文件哈希，要比 payload"；
- 性能上先拿到了 Python 侧最大的那块免费收益（16–20×），剩余瓶颈确认在
  Pillow 解码与 numpy 搬运，这才是 C++ 的真正收益来源；
- 仍缺：CLI 覆盖率（44%）、多数据集回归（2022/2024/2025 未全跑）、
  `pxc_core` 内部少量中文错误文本未迁移。

- 归档 8.39 GiB（1290 条目），erify 结果：**1290/1290 通过，失败 0**（770 个有损差分按内部近似像素校验）。

# 真实数据集上的第一轮优化（2026-10-31）

数据集清单由用户维护在 `<local-path>`，测试台 `tools/pxcs_suite.py`
可以把它们跑成可对比的 JSON 报告。

## 1. 发现：组 key 编码在主线程串行执行

`create_grouped_archive` 里 `write_group_key(state)` 是**同步调用**的：每组先把
key 编码完、写进归档，再把该组的变体提交给线程池。差分确实并行了，但 key 没有。

对 JPEG 数据集没影响（key 走 raw 直通，几十毫秒）；对 PNG 数据集是致命的：
一张 19 MP 的 RGBA 图 `webp_lossless(method=4)` 单张要 **9.1 秒**，几百个组就是
几百秒单核。实测 A09 跑到 25 分钟时进程 CPU 只有 **2.5 核 / 24 核**。

修复：key 编码提交到同一个线程池，但**严格按提交顺序落条目**，因此条目顺序与
串行版本一致（`tests/test_pxcs_limits.py::ParallelKeyOrderTests` 锁定）。

修复过程中还暴露并修掉了一个自己引入的提前退出 bug：当 `parallel_groups` 小于
组数、且窗口恰好排空时，主循环会直接 `break`，导致归档**静默缺条目**（A01
只写出 19/148）。现在循环末尾有一道断言：`next_group != len(image_groups)` 直接
抛错并 `writer.abort()`，绝不留半截归档。

## 2. 发现：无损差分走 PXC tile，GIL 全程占满

PNG 组差分是 q=0（无损），`residual_codec=auto` 会选 `pxc_residual`。它体积最小，
但是纯 Python/numpy 的逐 tile 实现，13 MP 一张约 10 秒，且几乎不能并行。

现在 `--residual-codec zlib` 对无损残差也生效。24 张 A09 子集实测：

| 残差编码器 | 耗时 | 产物 | 压缩率 |
|---|---:|---:|---:|
| `pxc_residual`（默认） | 190.6 s | 46.26 MiB | 23.15% |
| `zlib_residual` | 14.6 s | 53.60 MiB | 26.83% |

**快 13 倍、大 15.9%**。新增 `--fast` = `--residual-codec zlib`。

## 3. 前后对照

| 数据集 | 规模 | 优化前 | 优化后 | 说明 |
|---|---:|---|---|---|
| A01（JPG 散图） | 0.50 GiB / 148 | 12.0 s，98.92% | 12.2 s，98.92% | raw 直通，无变化 |
| A02（PNG 散图） | 0.56 GiB / 75 | 114.3 s，84.20% | **36.0 s**，84.20% | key 并行，3.2× |
| A08（JPG 差分） | 3.47 GiB / 565 | 266.8 s，50.20% | 277.2 s，50.20% | 噪声范围内，无回归 |
| A09（PNG 差分） | 3.68 GiB / 397 | >25 min 未完成 | **196.6 s**，39.65% | zlib 残差，397/397 校验通过 |

A09 的「优化前」无法给出干净耗时：第一次跑到 25 分钟时被手动终止，且当时
存在上面那个截断 bug。按 24 张子集的 `pxc_residual` 单张耗时外推，默认配置完整
跑完约需 50 分钟，即 `--fast` 大约快 15 倍。

## 4. 体积构成（最重要的一张表）

A08 归档 1785 MiB 的构成：

# 第二轮优化：按内容切分同分辨率大组（2026-10-31）

## 1. 发现：`residual_larger_than_source` 占了大头

给测试台加了 `by_reason` 统计后，A10 + A08 两个 JPEG 数据集合计：

| reason | 条目 | 源大小 | 占用 |
|---|---:|---:|---:|
| `residual_larger_than_source` | 636 | 4189M | 4189M（73.9%） |
| `residual_lossy` | 420 | 2573M | 741M |
| `key_lossy_passthrough` | 118 | 684M | 684M |

也就是说：**大量图片本来进了差分流程，但对着组 key 的残差没有变小，只好回退 raw。**

## 2. 根因：同分辨率不等于相似

分组键是 `(lossy, 宽, 高, 模式)`，一个组里可能混着几十个不同作品。
组内所有差分都对着**组首图**算，1 号作品的首图当然和 2 号作品不像。

对 A10 最大的那个组（347 张）做缩略图两两距离验证：

- 每张图和它最近邻的平均绝对差：中位数 **0.9**（32×32 灰度，满量程 255）；
- 40 张里有 39 张存在距离 < 8 的近邻。

**结论：近重复图一直都在，只是被分到了同一个组却互相不做差分。**

## 3. 修复：组内按缩略图再切一刀

`_split_similar_groups()`：对成员数 ≥ 8 的 JPEG 组，用 `Image.draft()` 快速降采样
生成 32×32 灰度缩略图，按贪心聚类（阈值 10）切成若干子簇，每个子簇一个 key。

- 缩略图生成走 `draft()`，只需约 1/8 的 DCT 解码；PNG 没有这条捷径，为分组
  整图解码太贵，所以**只对 JPEG 生效**；
- 成员数 < 8 的组不处理（收益不抵一次缩略图解码）；
- 聚类是确定性的：按自然序贪心，簇内保持原顺序；
- 合并错了也不会坏数据——残差超过源文件的 98% 仍然回退 raw；
- 可用 `--no-cluster` 关掉，回到旧行为。

## 4. 效果

| 数据集 | 优化前 | 优化后 | 变化 |
|---|---:|---:|---|
| **A10**（620 张 JPG） | 96.73%（140.4 s） | **25.32%**（128.5 s） | 体积 **-73.8%**，还更快了 |
| A08（565 张 JPG） | 50.20%（232.0 s） | **47.40%**（228.1 s） | 体积 -5.6% |

A10 的内部变化：组数 3 → 70，差分条目 33 → 549，raw 587 → 71。
`residual_larger_than_source` 从 636 条 / 4189M 降到 **10 条 / 92M**。

A08 的 raw 从 1061M 涨到…（实际 1488M → 1061M 的反向，见下表）：

| A08 | raw | 差分 |
|---|---:|---:|
| 优化前 | 1042M（167 条） | 2388M 源 → 687M |
| 优化后 | 1061M（173 条） | 2369M 源 → 568M |

差分的局部压缩率从 28.8% 降到 24.0%，整体 50.20% → 47.40%。

## 5. 顺带确认的两个否定结论

- **zlib level 9**：24 张子集上 54888 KiB → 54812 KiB（-0.14%），没有意义，不改默认；
- **本机没有可用的无损 JPEG 重压缩工具**：没有 `jpegtran` / `cjxl`，`pip install
  imagecodecs` 因代理不可用而失败，系统 ffmpeg（n4.3.2）也没有 libjxl。
  raw JPEG 的「再压 20%」这条路在离线环境里走不通。

## 6. 仍未做的

- 只在 12 个数据集上跑过（A14 / A15 在跑）；
- PNG 组还没有做相似度切分（缺 draft 捷径，需要另想办法）；
- `pxc_residual` 的 GIL 问题仍是绕开而非解决。

# 第五轮：JPEG XL 无损重打包（2026-10-31）

外网恢复后装上了 `imagecodecs`（内置 libjxl 0.11.2），它提供

## 1. 可行性验证

6 张真实 JPEG：编码后 **73.5%**，解码出来的字节与原始文件**完全相同**。
单线程编码约 7 MB/s、解码约 11 MB/s，可以按图并行。

## 2. 落地

- 新 codec `jpegxl`（HTTP payload 是 JXL 流，语义仍是"原始 JPEG 字节"）；
- `_raw_result()` 里统一尝试：只有省 ≥2% 才替换，否则保持 `raw`；
- `raw_crc32` / `source_sha256` 仍按原始字节计算，提取与校验都逐字节还原；
- 归档版本号：含 jpegxl 条目时写 **minor=4**（`--no-jxl` 仍写 1.2）；
- 依赖缺失时 `jxl.available()` 返回 False，自动回退 raw，不影响任何其它功能。

## 3. 结果

|---|---:|---:|---:|
| A01 | 98.92% | **83.49%** | 12.2 s → 18.2 s |

# 第六轮：verify 并行化（2026-10-31）

## 1. 问题

verify 一直是单线程的：A15（5842 条）校验要 18 分钟以上，期间 23 个核闲着。
引入 jpegxl 之后更贵——JXL 解码只有约 11 MB/s 单线程。

## 2. 做法

把 `verify_archive` 拆成三部分：

- `_verify_entry()`：单条目校验（原逻辑一字未改）；
- `_verify_range(start, stop)`：校验一段条目，**每个 worker 打开自己的
  ArchiveReader 和 resolver**（reader 持有文件句柄，共享会互相抢读写位置）；
- `verify_archive(..., threads=0)`：按条目数切片分发，合并结果。

边界：条目数 < 64 或加密归档走串行（加密每次都要重新派生 Argon2id 密钥，
多开 reader 得不偿失）。切片是连续区间，所以差分链基本不会被拆散。

## 3. 效果

A09 归档（397 条，zlib 残差）：

| 模式 | 耗时 | 结果 |
|---|---:|---|
| 串行 | 147.3 s | 397/397 通过 |
| 并行 | **59.8 s** | 397/397 通过，**2.46×** |

没到 24× 的原因：切片边界上的 key 会被相邻 slice 重新解码一次，加上解码
本身有 GIL 争用和磁盘 I/O。

## 4. 正确性

新增 `tests/test_pxcs_verify_parallel.py`：

- 并行与串行的 checked/failed 必须完全一致；
- 篡改一个 payload 后，并行校验必须能发现（`条目 CRC 校验失败`）。

# 第八轮：extract 并行化（2026-10-31）

## 1. 做法

和 verify 同一套切片：`_extract_one()` 抽单条目逻辑，`_extract_range(ids)` 由 worker
执行，每片打开自己的 ArchiveReader + resolver；主线程用 `as_completed` 汇总并推进度。

- 条目数 < 32 或加密归档 → 串行；
- `--verbose` 时保持串行（逐条打印会被并行打乱）。

## 2. 效果

A09 归档（397 条，1.31 GB，PNG 需要 WebP→PNG 重编码）：

| 模式 | 耗时 | 结果 |
|---|---:|---|
| 串行 | 621.2 s | 397 条全部提取 |
| 并行 | **107.8 s** | 397 条全部提取，**5.76×** |

PNG 重编码是 CPU 密集的，所以并行收益比 verify（2.46×）还高。

## 3. 正确性

新增 `tests/test_pxcs_extract_parallel.py`：

- 并行与串行提取出来的 70 个文件逐字节一致；
- 重复提取时"已存在就跳过"的语义不变（extracted=0, skipped=70）。

## 4. 顺带确认的否定结论

**PNG 关键帧不能换成 JXL 无损**：同样的 8 张 PNG，WebP lossless 15.47 MB，
JXL lossless 17.20 MB（**111%**），耗时差不多。WebP 在这类内容上更好，保持现状。

# 第九轮：当前的 CPU 利用率（2026-10-31）

用 `time.process_time()` 量进程总 CPU（含所有线程），除以墙钟和核数：

| 数据集 | 墙钟 | CPU | 占 24 核 | 吞吐 |
|---|---:|---:|---:|---:|
| A01（JPEG 散图，jxl） | 18.9 s | 129.0 s | 28.5% | 27.1 MB/s |
| A05（JPEG，jxl） | 60.2 s | 390.3 s | 27.0% | 27.6 MB/s |
| A09（PNG，zlib 残差） | 166.4 s | 1795.3 s | 45.0% | 22.7 MB/s |

结论：

- 相比最初的 **41.6%**，PNG 路径提升到 45%，但 **JPEG 路径只有 27–28%**；
- 已验证不是 jxl 的问题：8 线程编码 8 张 JPEG 有 **5.14×** 加速，说明它释放了 GIL；
- 剩下的是主线程的条目落盘路径（payload 复制、crc32/sha256、索引构建）与各组
  之间的调度开销。要真正吃满 24 核，仍然只有多进程一条路。

# 第十轮：内存基线补全（2026-10-31）

用 `GetProcessMemoryInfo` 读进程峰值工作集（必须在单数据集进程里跑，
`PeakWorkingSetSize` 是进程生命周期峰值）：

| 数据集 | 规模 | 峰值工作集 | 创建耗时 |
|---|---:|---:|---:|
| A01 | 0.50 GiB | 5.1 GB | 17.9 s |
| A05 | 1.62 GiB | 8.1 GB | 55.1 s |
| A09 | 3.68 GiB | 5.0 GB | 140.7 s |

峰值基本等于内存预算（可用物理内存的 60%），说明护栏是真的在"跑满预算"，
不是摆设。这也解释了为什么大图数据集里并行组会被内存压低——这是设计取舍：
宁可少用几个核，也不要被系统 OOM 杀掉。

顺带修掉一个测量 bug：`ctypes` 调 `GetProcessMemoryInfo` 时如果不声明
`argtypes`，64 位 HANDLE 会按默认 int 被截断，函数返回失败、结果恒为 0。
